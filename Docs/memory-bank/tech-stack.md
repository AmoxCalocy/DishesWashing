# 技术栈建议：洗碗时光

> 版本：0.9｜日期：2026-11-26｜适用范围：单人、第一人称、PC 端 3D 洗碗游戏的首个可玩版本

## 1. 推荐方案

项目固定使用 **Godot 4.7.2 标准版 + GDScript + Blender 5.3.0**，沿用现有厨房与餐具资产。编辑器、脚本、界面、音频和导出流程集中在同一引擎内，核心玩法无需服务器、数据库或大量第三方插件。

| 用途 | 推荐工具或方案 | 选择理由 |
| --- | --- | --- |
| 游戏引擎 | 固定 Godot 4.7.2 标准版及匹配导出模板 | 保持现有工程、团队与导出环境一致 |
| 编程语言 | GDScript，关键脚本使用静态类型标注 | 与引擎集成紧密，适合快速迭代；无需额外安装 .NET |
| 渲染 | 初始使用 Compatibility 渲染器 | 适合简单 3D 场景，优先覆盖较旧的桌面硬件；实际效果和性能需在目标机器验证 |
| 3D 建模 | Blender 5.3.0；通过 glTF 2.0（`.glb`）导入 | 制作厨房、餐具和简单动画，复用现有生成器与模型 |
| 界面与音频 | Godot 内置 Control 节点、AudioStreamPlayer 和音频总线 | 足以实现 HUD、设置、音效和音乐音量控制 |
| 存档 | Godot `FileAccess` + JSON，存于 `user://` | 本地保存设置和解锁进度；数据结构直观、便于排查 |
| 版本管理 | Git；大型二进制资源增长后按需启用 Git LFS | 保留可追溯的修改记录，控制大型资源对仓库的影响 |
| 首发构建 | Windows x86-64，使用 Godot 官方导出模板 | 与 PC 键鼠 MVP 范围一致；其他平台待验证后加入 |

记录实际运行版本，编辑器、团队成员和导出模板保持一致；升级前复制项目或创建分支并回归测试，不自动升级。正式发行前另行核对支持状态，参见 [Godot 发布策略](https://docs.godotengine.org/en/stable/about/release_policy.html)。

## 2. 为什么这样选择

本项目的难点是餐具操作与清洁反馈，而非开放世界、复杂角色动画或多人同步。Godot 的场景和节点模型足以支撑固定水槽、交互射线、工具、订单与 UI；使用 GDScript 也能减少搭建成本。

Compatibility 支持范围较广，但高级渲染功能较少，不能假设它在所有设备上最快。先用它制作风格化厨房，在目标硬件上测帧率和视觉效果；如果美术确实需要更高级的光照或效果，再在副本中评估 Forward+，并重新测试性能及兼容性。详见 [Godot 渲染器说明](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)。

Unity 是合理备选，尤其适合已有 Unity/C# 经验或现成资产的团队，但需要团队自行评估当前授权条款及工具链。Unreal Engine 适合强调高保真画面或已有 Unreal 经验的团队；对于当前小范围原型，其复杂度和资源开销可能更高。若团队已有其中一种引擎的成熟经验，优先沿用熟悉的工具往往比切换更省时。

## 3. 核心玩法落地

### 场景与交互

以下区分已验收的第 1～13 步、水槽堆放及追加操作原型与后续 MVP 目标；实际文件职责见 architecture.md。

- 保留生成的厨房展示器，玩法放在手工维护的 kitchen-game.tscn。CharacterBody3D 按镜头水平朝向行走，斜向归一化；玩家专用步行代理与真实表面查询分层。
- GameInput 只处理未被 UI 消费的事件；移动、鼠标观察、拖动旋转、Q/E 旋转轴与工具光标分别发送。菜单、失焦和模式变化清除持续输入，普通恢复捕获时丢弃首包鼠标位移。
- 左右两个稳定手位保存原实例及各自本次拿起来源。第一件左侧、第二件右侧，归回一件不调换另一件；支持两件餐具或餐具加一个清洗工具，泵瓶保持独占。普通搬运按 1／2 选择左右餐具，单件自动选中，第二件拿起保留原选择，空手／工具不可选；HUD 标注“当前”。确认放置及未来 Q 返回读取 selected_dish 和 get_selected_dish_item，而非 held_dish 兼容读取。
- 拿取前重新查询第一处实际表面，检查 1.5 米距离、遮挡和空手；注册位置从当前 SlotState 读取来源，水槽自由位置从原节点读取完整姿态；成功后清空原注册占用，标记 HELD 并移动同一实例。正在支撑上层餐具的下层须先移走上层。initial_slot_id 仅用于初始化。双手分别使用缓存网格包围盒、近裁剪余量和形状运动查询，在空间不足时拒绝拿取或保留最近安全姿态。
- 双持餐具和工具时，F 约 0.2 秒切换到沉浸模式：只移动餐具，不移动玩家、改变相机朝向或 FOV；只允许 F 返回搬运。近距离中键拖动及按住 Q/E 旋转，键盘旋转按物理时间处理；普通搬运旋转、角度／距离边界和滚轮仍在第 16 步补齐。game_rotate_close 独立绑定中键，右键 game_rotate 保留普通模式职责；沉浸右键不旋转、不放大，也不取消正在使用的工具。
- 沉浸中海绵和喷头闲置时共用相机前自由移动平面，按真实网格范围限制画面边缘并保留近裁剪余量；自由位置不依赖餐具角度、表面命中或是否离开表面。左键主动使用才转为真实接触／喷嘴瞄准，松开或旋转恢复自由移动；F 返回才恢复原手位。沉浸海绵仅移动鼠标时计擦洗并驱动压缩形态，当前尚不减污渍。
- 喷头拿起姿态单独配置，不复用餐盘朝向。动态软管连接实际 Hose_Exit 与 Hose_Attach，使用分段圆柱和端点切向曲线；每段只缩放自身局部长度轴，避免世界轴缩放将倾斜管段拉成长条。归位恢复模型原软管。当前是简化视觉跟随，长度约束、餐具避障和完整供水仍留在第 23 步。
- 普通模式持工具且对准已放餐具时，左键持续 use_tool；同持餐具时对准裸露槽底或架位则确认放置所选餐具。每个物理帧即时查询准星第一处真实表面，只操作未持有餐具；相机与 WASD 保持可用。海绵贴面持续擦动并压缩，喷头实际喷嘴瞄准命中点；两者复用沉浸的表面姿态计算，分别接受近裁剪、目标空间和接近路径检查，托盘边缘允许先抬高再接触，水槽内可先以安全搬运朝向抬升、检查旋转余量，再越过槽沿下降。contact_dish 记录本帧实际操作对象，contact_active 仍只代表操作反馈。
- 普通模式在 DISH/NONE 等目标之间移动时保留已按住的 use_tool 意图，实际无效命中立即停止接触，重新命中后继续；更换工具、模式、界面或失焦仍清除意图。松开左键立即回原手位，E 拿取前也先结束接触，避免工具留在餐具上妨碍拿取。
- 海绵与喷头通过世界左键或 E 拿取；普通模式持工具且未持餐具时，对准有效餐具按 E 优先拿到空手，其他持工具情形才尝试归回，检查世界原位距离和遮挡并保留另一手。近距离 E 属于旋转，不能归回。普通持餐具时 1／2 分派选中手位，其他上下文和 3 保留原意图，均不远程生成或切换实体工具；输入映射仍为 17 个。
- 右键 FOV 放大在空手、只持工具或独占持瓶时可用，缓存原 FOV 并在释放或中断时复原；持餐具时不触发放大。F 拉近餐具是独立的位置切换，不能与 FOV 混用。
- 第 17 步在 Compatibility 下验证只模糊环境的方案，工具、餐具、污渍、泡沫与 UI 保持清晰；记录边缘、透明材质和性能，不假定原生景深可用，不静默换渲染器。当前尚无环境模糊。
- 第 11 步共用只读判定现有两个入口：DishCarry.check_placement → PlacementRules.evaluate 检查注册位置，check_surface_placement → evaluate_surface 检查水槽自由落点。两者均使用显式选中手位，检查来源释放、1.5 米距离、视锥、真实遮挡和空间；注册位置另检查身份、兼容、空位与尺寸，只有沥水位调用真实 DishState.meets_cleanliness_requirement。缺少或错配清洁状态不授权入架，泡沫不参与；托盘来源和水槽自由位置允许脏餐具。正式订单状态仍未绑定场景，专项注入已知状态验证。
- 正式布局为 3 个托盘初始点和 8 个沥水架位，已移除两个固定水槽位及其标记。SlotConfig.maximum_dish_size 按餐具根局部轴记录米制尺寸，包含杯柄；11 个注册位置的盘／杯上限分别为（0.251，0.025，0.251）和（0.132，0.106，0.091）。固定目标查询只选沥水架；水槽通过真实盆体／排水口形状识别，排除同一碰撞体里的台面及边沿，不按餐具类型划分区域。
- 第 12 步自由姿态跟随真实命中 XZ，用 HandItem 缓存的八个底圈极值点向下查询支撑，接触点须包围餐具中心，浅坡按法线对齐，保留约 0.5 mm 间隙。过陡表面、支撑不足或最终网格穿插返回拒绝。空间先用包围盒筛选，再查询真实三角面的微薄凸棱柱，保留杯柄孔及小障碍检测；缓存几何形状以减少每帧构造，但不缓存判定，仍读取当前世界。这里不复用搬运 4 mm 余量，也不模拟插入轨迹或完整刚体平衡。
- PlacementPreview 只复制可见 MeshInstance3D，以独立绿／红材质和 HUD 原因反馈，不带碰撞、脚本或身份；固定架位用完整 marker 姿态，自由结果 slot_id 为空。GameInput 使用 PLACEMENT_SURFACE／STACKABLE_DISH，不增加键位：普通未持工具的餐具搬运瞄准水槽餐具时左键叠放、E 拿取；持工具瞄准餐具仍 use_tool，瞄准槽底或架位时可放下所持餐具。F、过渡、界面及失焦清除世界预览。
- 第 13 步确认前重新读取目标及共用规则，成功后同步移动原身体／碰撞、归入 PlayableDishes、记录 REGISTERED／BASIN 位置及支撑、更新架位占用及匹配 DishState 的 is_held／current_slot_id，最后只解除所选手位。失败不改场景或占用；同物理帧重复提交被阻止。自由位置直接由原节点 global_transform 记录，再次拿取保存 origin_kind、完整 origin_pose 及可选 origin_slot_id。DishCarry.dish_states 是预览和确认共同读取的引用入口，生产仍为空，不能默认清洁或加载 Examples 冒充订单。
- 水槽允许实体交叠堆放：初始槽底支撑后，对同一场景内 BASIN 餐具的实际底面采样，按 12×12 XZ 网格缓存最低真实顶点，精确三角形查询修正遗漏的边接触，必要时在已知上下界内细化高度。只缓存几何，不缓存授权；最终检查环境、工具和所有餐具，保留杯口／杯柄空隙。结果记录 support_dish_ids，拿取有上层依赖的下层餐具会被拒绝。此为静态自动落位，不做刚体滚动、倾倒或分类堆叠容量。
- PlacementResult 仍只是只读查询快照，不预留位置；实际变更仅由确认提交完成。第 14 步 Q 返回须使用所选手位的真实来源及最新支撑／距离／遮挡／空间判定，不能沿用旧结果。接入正式订单时仍须统一注册器与 OrderState 的占用所有权；实际供水与清洗尚未绑定。
- 供水阶段接入手动龙头、归位持续水流和手持喷头使用条件。世界 E 操作需与搬运 E 归回工具的优先级保持一致；实际供水须开关开启、有效范围、主动使用和真实餐具命中，不能把当前 contact_active 当作已出水。
- 海绵每单干燥，实际接触归位水流才湿润，本单保留、重开恢复；干海绵不去污。独占泵瓶须先放下餐具并归回工具，再空手拿取、单次泵压已放置餐具，Q 距离／遮挡合格才归位；每件有效施液赋予本单资格，不共享剂量或直接减污。
- Esc 与失焦现已阻止输入并保留持物；场景树、过渡及状态的完整冻结仍在第 18 步，不能将输入阻断写作完整暂停已实现。

### 污渍与清洁

首版确定使用**区域式污渍**：每个餐具表面配置多个较小区域，记录污渍类型、初始量、剩余量及泡沫残留；餐具实例单独记录本单施液资格。命中哪个区域，哪个区域的污渍整体渐淡，不提前实现逐像素擦除。实际命中必须关联区域，盘正反面与杯内分别可达；状态不与模型或其他实例共享。

后续普通与沉浸操作主动使用且命中区域时，依据同一组工具条件处理状态。喷水可清除残渣，对油渍的清除量恒为零；湿海绵擦洗可清除残渣，清除油渍另须该件已施液。普通模式由持续擦动动作提供运动，沉浸模式静止按住海绵不持续擦除；污渍变化按有效接触时间计算，不同帧率下保持一致，视觉和进度引用同一剩余量。当前仅动作和接触反馈已验收，供水、湿润和实际去污尚未绑定玩法。

湿海绵擦洗已施液餐具产生区域泡沫；喷头按命中逐步减少泡沫。泡沫是持久运行状态，粒子只是反馈，不能用粒子寿命代替残留量。泡沫按配置区域权重汇总为整件固定 0～100% 残留比例，反复施液或擦洗不抬高上限；切换、暂停、放下不清除残留。视觉、HUD 和结算引用同一数据。冲洗评分和点数折算采用设计文档第 7.3 节的首版可调方案，不做流体模拟。

全件清洁度只按初始污渍量加权计算，不混入泡沫；以实际值达到 95% 作为入架门槛，整数显示不改变判定。泡沫影响评分和实际点数，不禁止入架或结算。原型验证后再评估连续纹理遮罩；先保证手感，不为凑预计时长提高擦洗耗时。

### 订单与结算

使用 Godot 自定义 `Resource` 描述餐具类型、污渍配置和订单内容；运行时状态与静态配置分开。订单管理器根据餐具清洁度与放置状态计算进度，UI 通过信号响应状态变化。普通模式无需联网。

订单仅在所有餐具清洁度达标且当前入架后允许主动结算，未完成请求只提示原因，不扣分扣点。泡沫扣减只在成功结算时按快照计算一次，反复取放、重复点击不得重复扣减或发奖。解锁按订单完成记录，不以冲洗满分为前提。跳过教学可解锁两盘一杯，但不能冒充教学完成或领取其奖励。

## 4. 数据、工程与发布

### 存档

在 `user://` 保存带版本号的 JSON，包含设置、已解锁订单、点数、教学跳过与完成、首次奖励记录和预留外观；不要把存档写入项目目录。加载时校验字段类型并为缺失字段提供默认值，损坏文件保留备份并提示玩家。保存时先写临时文件，确认写入成功后再替换正式文件，并保留上一份备份；在目标系统上测试中断和替换失败。成功结算时将实得点数、完成及领取记录一起保存，修改设置后也保存；失败保留可用数据和待重试结果，重试不得重复加点。首版不保存进行中的订单，退出前提示进度重置。

### 目录与生成流程

沿用现有 Scenes、Scripts、Tools、Assets、Docs 目录及大小写；新增配置可放入 Resources，音频放入 Assets 下对应目录，不为套用示例搬迁既有资产。独立规则检查使用 Tools 下的验证脚本，并遵循 AGENTS.md 的命名约定。

保留现有厨房展示场景与浏览脚本，可玩场景单独接入。生成器负责的场景或资产发生变化时同步更新生成器，重建前保护手工编辑；可玩逻辑避免直接写入会被重建覆盖的展示文件。Blender 生成器通过 Blender 运行，运行时使用显式导出的 GLB。

提交 Godot 项目配置、场景、脚本、资源及必要的导入元数据；忽略 `.godot/` 等本机生成缓存和导出产物。Blender 源文件应有明确备份位置；团队若用 Git LFS，先配置追踪规则，再提交大型二进制文件，避免后期迁移成本。

### 开发与交付顺序

1. 核对固定工具链和现有展示基线，建立独立可玩入口与规则检查，不重新创建或覆盖现有项目。
2. 先准备独立状态与清洁度计算，再接入 WASD、玩家碰撞、鼠标直接看向及距离判定，然后完成盘杯拾取、近距离、环境模糊、旋转、槽位、放回和暂停。
3. 依次接入龙头开关、水流、海绵润湿、泵瓶拿取与施液、两类污渍、擦洗及泡沫冲净；验证正反面和杯内。
4. 加入订单、教学跳过、评分扣点、设置和存档；将中断测试放在对应功能完成后执行。
5. 以记录了配置的开发机、1080p、默认画质为临时性能基准，目标稳定 60 FPS；导出后在无编辑器的第二台 Windows 机器测试，最低配置后续确定，未测结果保留待验证。

## 5. 测试重点与风险

- **交互**：WASD 及斜向速度、玩家碰撞、直接鼠标看向、双手搬运、普通持工具持续瞄准和接触、E 拿取／归回优先级、移动后的距离和遮挡、近距离停止行走、工具自由移动与主动接触、F 双向切换、近距离中键及 Q/E 旋转，以及后续 Q 返回餐具、滚轮和近裁剪；检查界面和失焦恢复无漂移、误放或旧输入续用。
- **规则**：关水无效、实际接触水才润湿、先放下餐具再持瓶、有效泵压只施液到目标餐具、喷水不清除油渍、湿海绵与施液条件、区域渐淡、95% 临界值、泡沫评分与实际点数、完成与解锁条件。
- **存档**：首次启动、正常重启、缺失或损坏字段、写入失败与备份恢复。
- **兼容与性能**：至少在开发机和一台目标档次 Windows 机器上运行导出包；开发机先以 1080p 默认画质记录帧率，检查环境模糊、透明材质、UI 缩放和输入，不能仅凭启动无报错判定视觉或性能通过。
- **资源风险**：杯内和背面可能难以命中或观察；尽早制作真实形状的杯子进行测试。区域式污渍也可能显得过于块状，先试玩再决定是否升级。
