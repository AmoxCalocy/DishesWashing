# 技术栈建议：洗碗时光

> 版本：0.3｜日期：2026-11-23｜适用范围：单人、第一人称、PC 端 3D 洗碗游戏的首个可玩版本

## 1. 推荐方案

项目固定使用 **Godot 4.7.2 标准版 + GDScript + Blender 5.3.0**，沿用现有厨房与餐具资产。编辑器、脚本、界面、音频和导出流程集中在同一引擎内，核心玩法无需服务器、数据库或大量第三方插件。

| 用途 | 推荐工具或方案 | 选择理由 |
| --- | --- | --- |
| 游戏引擎 | 固定 Godot 4.7.2 标准版及匹配导出模板 | 保持现有工程、团队与导出环境一致 |
| 编程语言 | GDScript，关键脚本使用静态类型标注 | 与引擎集成紧密，适合快速迭代；无需额外安装 .NET |
| 渲染 | 初始使用 Compatibility 渲染器 | 适合简单 3D 场景，优先覆盖较旧的桌面硬件；实际效果和性能需在目标机器验证 |
| 3D 建模 | Blender 5.3.0；通过 glTF 2.0（`.glb`）导入 | 制作厨房、餐具和简单动画，复用现有生成器与模型 |
| 界面与音频 | Godot 内置 Control 节点、AudioStreamPlayer 和音频总线 | 足以实现 HUD、设置、音效和音乐音量控制 |
| 存档 | Godot `FileAccess` + JSON，存于 `user://` | 本地保存设置和解锁进度；数据结构直观、便于排查 |
| 版本管理 | Git；大型二进制资源增长后按需启用 Git LFS | 保留可追溯的修改记录，控制大型资源对仓库的影响 |
| 首发构建 | Windows x86-64，使用 Godot 官方导出模板 | 与 PC 键鼠 MVP 范围一致；其他平台待验证后加入 |

记录实际运行版本，编辑器、团队成员和导出模板保持一致；升级前复制项目或创建分支并回归测试，不自动升级。正式发行前另行核对支持状态，参见 [Godot 发布策略](https://docs.godotengine.org/en/stable/about/release_policy.html)。

## 2. 为什么这样选择

本项目的难点是餐具操作与清洁反馈，而非开放世界、复杂角色动画或多人同步。Godot 的场景和节点模型足以支撑固定水槽、交互射线、工具、订单与 UI；使用 GDScript 也能减少搭建成本。

Compatibility 支持范围较广，但高级渲染功能较少，不能假设它在所有设备上最快。先用它制作风格化厨房，在目标硬件上测帧率和视觉效果；如果美术确实需要更高级的光照或效果，再在副本中评估 Forward+，并重新测试性能及兼容性。详见 [Godot 渲染器说明](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)。

Unity 是合理备选，尤其适合已有 Unity/C# 经验或现成资产的团队，但需要团队自行评估当前授权条款及工具链。Unreal Engine 适合强调高保真画面或已有 Unreal 经验的团队；对于当前小范围原型，其复杂度和资源开销可能更高。若团队已有其中一种引擎的成熟经验，优先沿用熟悉的工具往往比切换更省时。

## 3. 核心玩法落地

### 场景与交互

- 将厨房、餐具、工具、污渍、沥水架和 UI 分别做成可复用场景。可玩场景使用 CharacterBody3D 管理玩家行走与碰撞，摄像机跟随玩家；保留现有展示器作为独立查看入口，不把固定机位控制直接当作玩家控制。
- WASD 根据镜头水平朝向移动，斜向输入归一化，使用物理时间更新位移并处理地面、墙体和柜体碰撞。普通状态捕获鼠标直接控制水平转向与有限俯仰，不需按右键；持餐具或泵瓶也可步行。近距离与切换期间停止行走，菜单、订单面板、暂停和失焦时阻止移动与场景输入，恢复时清除旧输入。
- 摄像机射线只检测可见且在交互距离内的目标；拾取、开关、泵压、润湿、放置与 Q 返回统一检查距离和遮挡。移动后重新计算预览，确认时再次校验，不能远距离归回餐具或泵瓶。喷头使用还需限制在水槽供水工作范围，不能携喷头无限走远；超出范围提示靠近后再清洁，不自动移动玩家。
- 悬空餐具采用普通拿起与近距离清洁两种状态。普通拿起挂在较远、偏下的搬运锚点，支持环顾与准星放置；按 F 仅将餐具拉至较近、居中的清洁锚点，不改变相机位置、观察方向或通过改变视角代替拉近。锁定镜头后鼠标控制操作光标，环境模糊而餐具、污渍、泡沫、工具与 UI 保持清晰。按 F 或 Q 返回搬运并解除模糊；左键放置、Q 安全放回。
- 环境模糊先在 Compatibility 下做图形验证，选择能单独处理背景的方案，并检查边缘、透明材质、输入射线与性能；不能假定某项原生景深效果在当前渲染器可用，不能静默切换渲染器或省略模糊需求。
- 两个锚点共用同一件餐具实例，保留旋转、污渍进度和工具选择。按餐具尺寸配置观察距离与近距离滚轮范围，以完整展示餐具并避开摄像机近裁剪面。初始过渡约 0.2 秒，期间阻止放置、清洁和重复切换。普通拿起的放置射线排除当前餐具与工具，近距离射线检测当前餐具表面；有效落点仍需检查尺寸、占用和清洁度规则。
- 海绵、喷头作为独立可见物体跟随表面命中点，海绵按表面朝向贴合并轻微压缩，喷头从喷嘴向冲洗点发射水流。清洁判定与可见接触点使用同一目标，排除工具自身对检测射线的遮挡；失去有效命中时停止清洁并撤回工具。2026-11-11 确定采用这套悬空方案，取消手部模型、骨骼绑定和抓握动画的制作需求。
- 用 Input Map 定义拾取、放置、使用工具、旋转、切换拿起状态、返回和暂停等动作。左键按当前持有物、模式及目标执行拾取、润湿、放置、泵压或清洁；一次输入只执行一个动作，UI 消费的输入不传给场景。右键旋转期间暂停环顾与清洁并撤回工具；切换、旋转、暂停或失焦恢复后清除旧输入，要求重新按下左键。
- 水龙头初始关闭，空手或搬运时瞄准开关显示 E 开启或关闭提示，单次按键只切换一次。喷头归位且开关开启时持续固定出水；近距离手持喷头须同时具备开关开启、有效命中和主动使用才喷水。退出近距离停止手持喷水，但不自动关龙头；喷头归位后恢复相应固定水流。暂停时冻结水流表现与润湿判定。
- 海绵每单默认干燥；空手选择海绵、瞄准归位喷头的实际水流并按住左键，将可见海绵移入水流，实际接触后才设为湿润。本单保留湿润，换工具或餐具不恢复干燥；重开订单恢复干燥。干海绵不清除污渍。
- 泵瓶是单独手持物。必须先放下餐具，空手瞄准瓶子按 E 拿起，左键单次泵压至距离内可见的已放置餐具；Q 检查固定瓶位的距离与遮挡，可归回时才归位，否则继续持瓶并提示靠近。持瓶不能同时持餐具或工具，也不能按 F 进入餐具近距离；泵压期间忽略重复输入，复用现有按压动画及出液节点。每件接受有效施液后取得本单资格，湿海绵可清洗该件各面油渍；不把资格传给其他餐具，不模拟剂量或耗尽，冲洗只消除泡沫。

### 污渍与清洁

首版确定使用**区域式污渍**：每个餐具表面配置多个较小区域，记录污渍类型、初始量、剩余量及泡沫残留；餐具实例单独记录本单施液资格。命中哪个区域，哪个区域的污渍整体渐淡，不提前实现逐像素擦除。实际命中必须关联区域，盘正反面与杯内分别可达；状态不与模型或其他实例共享。

玩家处于近距离、主动使用且命中区域时，依据工具与条件处理状态。喷水可清除残渣，对油渍的清除量恒为零；湿海绵移动擦洗可清除残渣，清除油渍另须该件已施液。污渍变化按接触时间计算，静止按住海绵不持续擦除；不同帧率下保持一致。视觉和进度引用同一剩余量。

湿海绵擦洗已施液餐具产生区域泡沫；喷头按命中逐步减少泡沫。泡沫是持久运行状态，粒子只是反馈，不能用粒子寿命代替残留量。泡沫按配置区域权重汇总为整件固定 0～100% 残留比例，反复施液或擦洗不抬高上限；切换、暂停、放下不清除残留。视觉、HUD 和结算引用同一数据。冲洗评分和点数折算采用设计文档第 7.3 节的首版可调方案，不做流体模拟。

全件清洁度只按初始污渍量加权计算，不混入泡沫；以实际值达到 95% 作为入架门槛，整数显示不改变判定。泡沫影响评分和实际点数，不禁止入架或结算。原型验证后再评估连续纹理遮罩；先保证手感，不为凑预计时长提高擦洗耗时。

### 订单与结算

使用 Godot 自定义 `Resource` 描述餐具类型、污渍配置和订单内容；运行时状态与静态配置分开。订单管理器根据餐具清洁度与放置状态计算进度，UI 通过信号响应状态变化。普通模式无需联网。

订单仅在所有餐具清洁度达标且当前入架后允许主动结算，未完成请求只提示原因，不扣分扣点。泡沫扣减只在成功结算时按快照计算一次，反复取放、重复点击不得重复扣减或发奖。解锁按订单完成记录，不以冲洗满分为前提。跳过教学可解锁两盘一杯，但不能冒充教学完成或领取其奖励。

## 4. 数据、工程与发布

### 存档

在 `user://` 保存带版本号的 JSON，包含设置、已解锁订单、点数、教学跳过与完成、首次奖励记录和预留外观；不要把存档写入项目目录。加载时校验字段类型并为缺失字段提供默认值，损坏文件保留备份并提示玩家。保存时先写临时文件，确认写入成功后再替换正式文件，并保留上一份备份；在目标系统上测试中断和替换失败。成功结算时将实得点数、完成及领取记录一起保存，修改设置后也保存；失败保留可用数据和待重试结果，重试不得重复加点。首版不保存进行中的订单，退出前提示进度重置。

### 目录与生成流程

沿用现有 Scenes、Scripts、Tools、Assets、Docs 目录及大小写；新增配置可放入 Resources，音频放入 Assets 下对应目录，不为套用示例搬迁既有资产。独立规则检查使用 Tools 下的验证脚本，并遵循 AGENTS.md 的命名约定。

保留现有厨房展示场景与浏览脚本，可玩场景单独接入。生成器负责的场景或资产发生变化时同步更新生成器，重建前保护手工编辑；可玩逻辑避免直接写入会被重建覆盖的展示文件。Blender 生成器通过 Blender 运行，运行时使用显式导出的 GLB。

提交 Godot 项目配置、场景、脚本、资源及必要的导入元数据；忽略 `.godot/` 等本机生成缓存和导出产物。Blender 源文件应有明确备份位置；团队若用 Git LFS，先配置追踪规则，再提交大型二进制文件，避免后期迁移成本。

### 开发与交付顺序

1. 核对固定工具链和现有展示基线，建立独立可玩入口与规则检查，不重新创建或覆盖现有项目。
2. 先准备独立状态与清洁度计算，再接入 WASD、玩家碰撞、鼠标直接看向及距离判定，然后完成盘杯拾取、近距离、环境模糊、旋转、槽位、放回和暂停。
3. 依次接入龙头开关、水流、海绵润湿、泵瓶拿取与施液、两类污渍、擦洗及泡沫冲净；验证正反面和杯内。
4. 加入订单、教学跳过、评分扣点、设置和存档；将中断测试放在对应功能完成后执行。
5. 以记录了配置的开发机、1080p、默认画质为临时性能基准，目标稳定 60 FPS；导出后在无编辑器的第二台 Windows 机器测试，最低配置后续确定，未测结果保留待验证。

## 5. 测试重点与风险

- **交互**：WASD 及斜向速度、玩家碰撞、直接鼠标看向、普通搬运、移动后的距离和遮挡、近距离停止行走、工具接触、F 双向切换、Q 返回、滚轮及近裁剪；检查暂停、界面和失焦恢复无漂移、误放或自动清洁。
- **规则**：关水无效、实际接触水才润湿、先放下餐具再持瓶、有效泵压只施液到目标餐具、喷水不清除油渍、湿海绵与施液条件、区域渐淡、95% 临界值、泡沫评分与实际点数、完成与解锁条件。
- **存档**：首次启动、正常重启、缺失或损坏字段、写入失败与备份恢复。
- **兼容与性能**：至少在开发机和一台目标档次 Windows 机器上运行导出包；开发机先以 1080p 默认画质记录帧率，检查环境模糊、透明材质、UI 缩放和输入，不能仅凭启动无报错判定视觉或性能通过。
- **资源风险**：杯内和背面可能难以命中或观察；尽早制作真实形状的杯子进行测试。区域式污渍也可能显得过于块状，先试玩再决定是否升级。
