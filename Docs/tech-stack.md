# 技术栈建议：洗碗时光

> 版本：0.1｜日期：2026-11-06｜适用范围：单人、第一人称、PC 端 3D 洗碗游戏的首个可玩版本

## 1. 推荐方案

首选 **Godot 4.7 稳定版 + GDScript + Blender**。这套组合适合小团队快速制作单机 3D 原型：编辑器、脚本、界面、音频和导出流程集中在同一引擎内，核心玩法无需服务器、数据库或大量第三方插件。

| 用途 | 推荐工具或方案 | 选择理由 |
| --- | --- | --- |
| 游戏引擎 | Godot 4.7 稳定分支的最新补丁版，标准版 | 自带 3D 场景、物理查询、UI、音频与 Windows 导出；开源且可免费使用 |
| 编程语言 | GDScript，关键脚本使用静态类型标注 | 与引擎集成紧密，适合快速迭代；无需额外安装 .NET |
| 渲染 | 初始使用 Compatibility 渲染器 | 适合简单 3D 场景，优先覆盖较旧的桌面硬件；实际效果和性能需在目标机器验证 |
| 3D 建模 | Blender；通过 glTF 2.0（`.glb`）导入 | 制作厨房、餐具和简单动画，格式易于在工具间交换 |
| 界面与音频 | Godot 内置 Control 节点、AudioStreamPlayer 和音频总线 | 足以实现 HUD、设置、音效和音乐音量控制 |
| 存档 | Godot `FileAccess` + JSON，存于 `user://` | 本地保存设置和解锁进度；数据结构直观、便于排查 |
| 版本管理 | Git；大型二进制资源增长后按需启用 Git LFS | 保留可追溯的修改记录，控制大型资源对仓库的影响 |
| 首发构建 | Windows x86-64，使用 Godot 官方导出模板 | 与 PC 键鼠 MVP 范围一致；其他平台待验证后加入 |

Godot 官方发布策略将 4.7 列为受支持分支，并建议新项目使用 4.x。项目创建时记录**具体补丁版本**，编辑器、团队成员和导出模板保持一致；升级前复制项目或创建分支并回归测试，不自动追随开发版。Godot 的小版本支持期限并非传统固定年限的 LTS 承诺，正式发行前应重新核对支持状态。参见 [Godot 发布策略](https://docs.godotengine.org/en/stable/about/release_policy.html)。

## 2. 为什么这样选择

本项目的难点是餐具操作与清洁反馈，而非开放世界、复杂角色动画或多人同步。Godot 的场景和节点模型足以支撑固定水槽、交互射线、工具、订单与 UI；使用 GDScript 也能减少搭建成本。

Compatibility 支持范围较广，但高级渲染功能较少，不能假设它在所有设备上最快。先用它制作风格化厨房，在目标硬件上测帧率和视觉效果；如果美术确实需要更高级的光照或效果，再在副本中评估 Forward+，并重新测试性能及兼容性。详见 [Godot 渲染器说明](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)。

Unity 是合理备选，尤其适合已有 Unity/C# 经验或现成资产的团队，但需要团队自行评估当前授权条款及工具链。Unreal Engine 适合强调高保真画面或已有 Unreal 经验的团队；对于当前小范围原型，其复杂度和资源开销可能更高。若团队已有其中一种引擎的成熟经验，优先沿用熟悉的工具往往比切换更省时。

## 3. 核心玩法落地

### 场景与交互

- 将厨房、餐具、工具、污渍、沥水架和 UI 分别做成可复用场景。玩家固定在水槽前，使用摄像机射线检测交互目标；通过碰撞层区分餐具、工具和环境。
- 悬空餐具采用普通拿起与近距离清洁两种状态。普通拿起挂在较远、偏下的搬运锚点，支持环顾与准星放置；按 F 切换到较近、居中的清洁锚点，此时锁定镜头，由鼠标控制操作光标。按 F 或 Q 从近距离返回普通拿起，恢复进入前的环顾朝向；普通拿起时左键放置，Q 尝试放回安全位置。
- 两个锚点共用同一件餐具实例，保留旋转、污渍进度和工具选择。按餐具尺寸配置观察距离与近距离滚轮范围，以完整展示餐具并避开摄像机近裁剪面。初始过渡约 0.2 秒，期间阻止放置、清洁和重复切换。普通拿起的放置射线排除当前餐具与工具，近距离射线检测当前餐具表面；有效落点仍需检查尺寸、占用和清洁度规则。
- 海绵、喷头作为独立可见物体跟随表面命中点，海绵按表面朝向贴合并轻微压缩，喷头从喷嘴向冲洗点发射水流。清洁判定与可见接触点使用同一目标，排除工具自身对检测射线的遮挡；失去有效命中时停止清洁并撤回工具。2026-11-11 确定采用这套悬空方案，取消手部模型、骨骼绑定和抓握动画的制作需求。
- 用 Input Map 定义拾取、放置、使用工具、旋转、切换拿起状态、返回和暂停等动作。左键按状态执行拾取、放置或清洁，右键旋转期间暂停环顾与清洁并撤回工具。清洁仅在近距离状态生效；退出该状态时停止水流、擦洗声和接触效果。切换、旋转或暂停恢复后清除旧的使用状态，要求重新按下左键再清洁。

### 污渍与清洁

先实现**区域式污渍**：每个餐具表面配置多个小污渍区域，每个区域记录类型、初始量、剩余量和是否已涂洗洁精。污渍可以使用附着在餐具上的小网格或材质表现；实际工具命中需要关联到对应区域，不能仅根据整件餐具碰撞推算局部位置。

玩家处于近距离清洁状态、按住使用键且射线命中区域时，依据工具、污渍类型、洗洁精状态和帧间时间减少剩余量；海绵擦洗还需检测鼠标移动。用同一份剩余量驱动视觉变化与清洁度，避免显示和判定不一致。盘子正反面和杯内都应分别可命中。水流、泡沫先用粒子和声音表现，不进行流体模拟。

全件清洁度按设计文档的初始污渍量加权计算；达到 95% 才能放入沥水架并记为完成。原型验证通过后，如果区域式效果不够细腻，再评估纹理遮罩擦除：需单独验证 UV 接缝、正反面、性能和渲染器兼容性，不提前引入复杂方案。

### 订单与结算

使用 Godot 自定义 `Resource` 描述餐具类型、污渍配置和订单内容；运行时状态与静态配置分开。订单管理器根据餐具清洁度与放置状态计算进度，UI 通过信号响应状态变化。普通模式无需联网。

现有游戏设计文档对未完成时是否允许结算存在两种表述：核心循环提到扣除奖励，MVP 验收标准要求全部完成后结算。建议原型先按 **全部完成后才能结算** 实现，待玩法确定后统一设计文档。

## 4. 数据、工程与发布

### 存档

在 `user://` 保存带版本号的 JSON，包含设置、已解锁订单、点数和已选外观；不要把存档写入项目目录。加载时校验字段类型并为缺失字段提供默认值，损坏文件保留备份并提示玩家。保存时先写临时文件，确认写入成功后再替换正式文件，并保留上一份备份；在目标系统上测试中断和替换失败的处理。订单完成时自动保存；首版不保存进行中的订单，退出前提示进度重置。

### 推荐目录

```text
project.godot
scenes/          # 厨房、餐具、工具、界面场景
scripts/         # 交互、清洁、订单与存档逻辑
resources/       # 订单、餐具和污渍配置
assets/models/   # 导入的 .glb
assets/textures/ # 纹理
assets/audio/    # 音效与音乐
tests/           # 关键规则测试或测试场景
docs/            # 后续补充的制作说明
```

提交 Godot 项目配置、场景、脚本、资源及必要的导入元数据；忽略 `.godot/` 等本机生成缓存和导出产物。Blender 源文件应有明确备份位置；团队若用 Git LFS，先配置追踪规则，再提交大型二进制文件，避免后期迁移成本。

### 开发与交付顺序

1. 安装固定版本的 Godot 标准版、对应导出模板、Blender 和 Git；记录版本。新建 Windows 项目并先验证空项目可导出运行。
2. 用简单几何体完成普通拿起、近距离切换、旋转、放回与槽位吸附；再加入盘子和杯子。
3. 实现两类污渍和工具，检查正反面、杯内、95% 阈值与清洁反馈。
4. 加入订单、教学、暂停、结算和存档，在全新存档及已有存档下验证完整一局。
5. 导出 Windows 构建，在未安装编辑器的目标机器测试。记录 CPU、GPU、内存、分辨率、画质及帧率；以稳定 60 FPS 为初始目标，测试后再确定最低配置。

## 5. 测试重点与风险

- **交互**：普通拿起的环顾与放置、近距离的工具接触、F 双向切换、Q 按状态返回、滚轮边界和不同尺寸餐具的近裁剪。检查快速切换、按住左键切换、旋转及暂停恢复，确保进度和朝向保留、清洁正确停止，且不会误放餐具。
- **规则**：残渣和油渍的工具条件、污渍加权计算、95% 临界值、放置与订单完成条件。
- **存档**：首次启动、正常重启、缺失或损坏字段、写入失败与备份恢复。
- **兼容与性能**：至少在开发机和一台目标档次 Windows 机器上运行导出包；检查 UI 缩放、输入、帧率和效果。
- **资源风险**：杯内和背面可能难以命中或观察；尽早制作真实形状的杯子进行测试。区域式污渍也可能显得过于块状，先试玩再决定是否升级。
